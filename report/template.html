1. Approach and why

pages ─► classify p1 ─► Qwen3-VL-8B (4-bit, MLX), per-type prompt, all pages in one call ─► column roles + 2 repairs ─► normalise
                                           PaddleOCR-VL reads each page ─► "value not on the page" ─► review flags
  • Zero-shot VLM, not OCR + rules. In a 40-doc bake-off covering all 18 suppliers (note 09), Qwen3-VL-8B read supplier part numbers exactly 98.9% (digital) / 92.3% (scanned) of the time, above the ceiling of PP-OCRv5 (95.1 / 86.0: a value OCR never emits can't be extracted). It got 100% of header fields and 0 of 15 false fills on illegible fields with no rules at all.
  • No fine-tuning. Train has 18 suppliers whose ~40-part catalogues are reused in 99% of dev rows (note 02), so a tuned model would learn to recall catalogues, which is exactly what fails on unseen suppliers. It would also cost a GPU we chose not to rent.
  • Field meaning from the model, formats from code. The invoice prompt asks the model to name each column's role from the seller's point of view ("Your/Customer" = buyer) before it fills rows. This targets the costliest error (one swapped column zeroes every row). Code then does dates (ISO, ambiguous day/month flagged), numbers (incl. European 1.234,50), currency and IATA codes. No rule mentions a supplier, prefix or layout position.
  • Sized for 24 GB. Size sweep (note 11): 2B 55.5 OVERALL with false fills, 4B 84.0, 8B 4-bit 90.5, 8B 8-bit 89.4 (40-doc bake-off). With the final prompt, 8B 4-bit scored 91.0 vs 90.3 for 8-bit, with 0 vs 1 false fill, at 19 vs 31 s/doc and a 7.5 vs 11.9 GB peak. We kept 4-bit, which leaves about two-thirds of the 24 GB free. The quantisation risk is real but not decisive: both widths read PO as P0 on one invoice.
  • Null only when obscured. Null on a readable field scores like a wrong value (note 07), so readable-but-uncertain values are kept and flagged; only absent, blacked-out or scribbled values are null.

4. A new supplier layout

  • Nothing to retrain. The prompt describes field meanings (seller vs buyer part number, PO even when it looks like a part number, totals only from the labelled total), not layouts; header wordings appear only as examples. A new layout goes through as-is, and fold 4 measures exactly this.
  • Monitor, then fix generically. Review-flag rates per supplier show a new layout that reads badly. A fix is a meaning rule or a repair that holds for any layout (as the two existing column repairs do), checked on a held-out fold before it ships, never a supplier-specific rule.
  • Volume. At ~10k docs/day this design moves to a 24 GB GPU with vLLM batching and JSON-schema-constrained decoding (note 10); that path is a recommendation, untested here.

6. Limits and honesty

  • I looked at all 18 train suppliers while analysing the data, and the column-role prompt and its three fixes were written after reading bake-off errors (fold-4 docs excluded). Dev numbers are therefore optimistic. The fold-4 row is the cleanest unseen estimate, but it has only {{F4N}} docs.
  • Throughput on the Mac: {{THROUGHPUT}}. The transformers backend (--backend hf) for graders without a Mac is implemented but was not run.
  • Cut for time: a faster prompt (v2, compact output) that turned out slower and was not used; scan upscaling; a second OCR tier for high-precision flags.
